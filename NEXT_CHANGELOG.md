# Next Changelog for CoCart Android SDK <!-- omit in toc -->

> [!WARNING]
> This changelog is **NOT** final. It lists the changes waiting for the first release of `com.cocart:sdk`, to be moved into `CHANGELOG.md` under the new version when it's released.

## Added

- Product methods for the rest of the CoCart Starter routes: `variations()`, `categories()`, `category(id)`, `tags()`, `tag(id)`, `attributes()`, `attribute()`, `attributeTerms()`, `attributeTerm()`, `attributeBySlug()`, `attributeTermsBySlug()`, `attributeTermBySlug()`, `reviews()`, `productReviews()`, `seo()` and `seoBySlug()` (CoCart SEO Pack), and the listing shortcuts `search()`, `byCategory()`, `byTag()`, `featured()`, `onSale()`, `byPriceRange()`, `sortBy()`, `byStockStatus()` and `paginate()`. `ProductOrderBy` lists the sort orders CoCart accepts, with `SortOrder` and `StockStatus`. `find()`, `findBySlug()`, `variation()`, `brands()` and `brand()` take optional query parameters.
- Methods for the CoCart Plus 2.0 routes: `cart().getMini()`, `cart().removeCoupons()`, `cart().removeAllItems()` (keeps coupons and fees), `products().shippingRates()`, `products().createReview()`, `sessions().getItems()`, and on `account()`: `register()`, `updateAddress()`, `cancelOrder()`, `verifyEmail()`, `sendOrderEmailVerification()`, `verifyOrderEmail()`, the subscription methods (`getSubscriptions()`, `getSubscription()`, `suspendSubscription()`, `reactivateSubscription()`, `cancelSubscription()`, `setSubscriptionAutoRenew()`, `updateSubscriptionPaymentMethod()`, `resubscribe()`, `cancelResubscribe()`) and `requestOrderWithdrawal()`.
- `applyCoupon()` and `checkCoupons()` take an optional email for coupons restricted to certain emails; `addFee()` takes an optional tax class.
- **Choices for CoCart Plus's supported plugins.** `addItem()`'s options are documented for a subscription plan (`convert_to_sub`), a gift recipient (`recipient_email`) and a warranty (`item_data` `warranty`); other plugins' fields still pass through. `cart().changePlan(itemKey, value)` switches a cart item to another plan, or to one-time with `"0"`.
- `CoCartResponse.toList()` reads the routes that answer with a list (categories, tags, attributes, reviews, variations), and `get()` takes an index first for them (`get("0.name")`).
- Response helpers for the shapes CoCart sends: `getNotices()` (keyed by type), `getShippingMethods()` (the packages as a list), `getShipping()`, `getFees()` (as a list), `getExtensions()`, `getRateLimit()` (`RateLimitInfo`) and `getHeader()`. Header names are matched without regard to case, as HTTP/2 sends them lowercase.
- **A guest cart that no longer exists is replaced automatically.** CoCart Starter 5 refuses a cart key with no cart session on every cart route (`cocart_invalid_cart`), for example after the cart expired. The client then forgets the stored cart key and retries the request once as a new guest.
- `CoCartException.errorCode()` returns the API error code, and `getCart()` the cart sent with an error: `cocart_item_not_in_cart` carries the current cart since CoCart Starter 5. `getFields()` returns every field at fault (`data.fields`, as path to message, empty when there are none), `getField()` the first one (`data.field`) and `getReason()` the plugin's own reason (`data.reason`), each `null` when absent. A 400 throws `ValidationException` and a 401 or 403 `AuthException`, each with the response data; a 409, 429 or 5xx is never a `ValidationException`. An error's message names the method and route (never the query string) with the API's message and code, e.g. `POST /cocart/v2/checkout: … [cocart_invalid_address_fields]`. `RateLimitException` carries the response data too.
- `docs/extension-data.md` lists the data CoCart Plus adds under `extensions` for the plugins it supports, and how to send the customer's choices.
- **Checkout (CoCart Plus 2.0).** `client.checkout()` places orders and takes payment: `placeOrder()` with `payment_data` (the gateway's tokens only) as a map of the keys the gateway reads (`"wc-stripe-payment-method" to paymentMethod.id`), and a free order needs neither `payment_data` nor `payment_method`. It returns a `CheckoutResult` read from the response's `result`: `code` (`order_placed`, `action_required`, `payment_pending`, `payment_failed`, or `payment_method_changed` for a subscription), `isComplete`, `isAwaitingPayment` (the order is placed and the customer pays outside the checkout: Cash App Pay, WeChat Pay, Stripe vouchers, BLIK…), `needsConfirmation` for 3D Secure, `needsRedirect` for an off-site step, `isPending`, `isFailed`, `objectType` (`order` or `subscription`), `orderId`, `orderKey`, `orderNumber`, `orderStatus`, `subscriptionId`, `redirectUrl` (https or http only), `clientSecret`, `intentType`, `paymentMethodType`, `message`, `errorCode`, `gatewayErrorCode`, `gatewayMessage`, `actionType`, `actionData` and `response`. A declined card is a result to read, not an exception, and printing a result never shows `clientSecret` or `orderKey`. `payForOrder()` (including 3D Secure) and `confirmReturn()` return the same result; both send the order key in the body. Also `get()` (optional `currency`, `formatted` and `thumb`; call it for the review screen, as it snapshots the total), `update()`, `process()`, `getConfig()`, `getPaymentMethods()`, `getSavedPaymentMethods()` (`SavedPaymentMethod`, with `label`, e.g. "Visa ending in 4242"), `searchAddresses()`, `getAddressDetails()`, `getOrderReceived()` (optional `formatted` and `meta_keys`) and `confirmOrderPayment()`. No payment SDK dependency: see `docs/checkout.md` for using stripe-android with it.
- **Checkout: finding out how an order ended when no answer came back.** `placeOrder()` sends each order with a random `checkout_id` (or yours, in the input: 16 to 64 letters, digits, `-` or `_`, else `checkout_invalid_checkout_id` before anything is sent). When the connection drops, the request times out, a proxy gives up waiting, or another request is still taking payment for the cart (`409 cocart_payment_in_progress`), it throws `CheckoutOutcomeUnknownException` (a `CoCartException`) with `checkoutId`, and `checkout().getStatus(checkoutId)` asks CoCart Plus 2.0 how it ended (`CheckoutStatus`: `code` `order_placed`, `payment_required`, `in_progress` or `not_placed`, `message`, and the order's `orderId`, `orderKey`, `orderNumber` and `orderStatus`).
- `account().updateSubscriptionPaymentMethod()` takes a new card in `payment_data` as well as a saved card's `token_id`, and returns a `CheckoutResult` read from the subscription the response sends (`payment_method_changed`, with `subscriptionId`), since a new card may need 3D Secure.
- **Account reads for CoCart Plus 2.0.** `getOrders()` takes `status` (one or a list, comma-joined), `after`, `before`, `subscription_order_type`, `formatted` and `meta_keys` as well as `page`, `per_page` and `order`; `getSubscriptions()` takes `status`, `formatted` and `meta_keys`; `getProfile()`, `getOrder()`, `getGuestOrder()` and `getSubscription()` take optional `formatted` and `meta_keys`. `getOrderDownloads()` and `getGuestOrderDownloads()` read `my-account/orders/{id}/downloads` (with the billing email for a guest) and return the response as sent (`{ "downloads": [...] }`), like `getDownloads()`. `changePassword()` sends only `password_current`, `password_1` and `password_2`.
- **Client hardening for CoCart Plus 2.0.** A retry after a 429 waits as long as `RateLimit-Retry-After` (what CoCart Plus sends), or else `Retry-After`, says, up to 60 seconds. Debug output shows every query value as `***`, so cart keys, order keys and emails stay out of logs; events keep the full URL, and listeners mustn't forward it. The ETag cache never keeps a response marked `no-store` or `private`. CoCart Plus, account and JWT requests (the full-route requests) emit the same `REQUEST`, `RESPONSE` and `ERROR` events as the others, the `RESPONSE` event carries the `CoCartResponse` (`response`) for every answer, errors included, and they're never sent again by the client.
